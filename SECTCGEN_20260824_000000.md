## SEC_API_AUTH_001 — Authentication on Critical Workflow Start

**Test Case ID**  
SEC_API_AUTH_001

**Test Case Name**  
Verify Workflow Start Requires Valid Authentication

**API Name**  
OpenAPI definition

**Endpoint**  
/api/v1/workflows/{id}/start

**HTTP Method**  
POST

**Operation ID**  
startExecution

**Security Category**  
Authentication

**OWASP Mapping**  
API2:2023, API3:2023, API5:2023

**CWE Mapping**  
CWE-306 (Missing Authentication for Critical Function)

**Security Objective**  
Ensure workflow execution cannot be started without a valid, non-expired, correctly scoped token.

**Risk**  
Critical

**Priority**  
P1

**Preconditions**  
- A workflow definition with ID `{workflowId}` exists.  
- Authentication mechanism exists (JWT/OAuth/API key) — details unknown.

**Authentication Context**  
- Valid token for Standard User A.  
- Invalid token (random string).  
- Expired token.  
- Missing token.

**Required User / Role**  
Standard User A (role model unknown — role context required).

**Required Tenant Context**  
Tenant A for Standard User A (tenant model unknown — context required).

**Required Test Data**  
- `{workflowId}` that Standard User A is allowed to start.

**Request Headers**  
- `Authorization: Bearer {{validUserAToken}}` (for positive case).  
- For negative cases: missing header, malformed header, `Bearer {{invalidToken}}`.

**Path Parameters**  
- `id = {{workflowId}}`

**Query Parameters**  
- None.

**Request Body**  
Example minimal valid body (structure inferred):
```json
{
  "user": "{{userAId}}",
  "realmId": "tenantA",
  "hierarchyLevel": "LEVEL_1",
  "hierarchyEntityId": "ENTITY_1",
  "userInputs": {
    "field1": "value1"
  }
}
```

**Security Manipulation**  
- Remove Authorization header.  
- Use empty `Authorization` header.  
- Use malformed header `Auth: Bearer token`.  
- Use invalid/expired token.  
- Use wrong audience/issuer token (if known).

**Execution Steps**  
1. Send POST `/api/v1/workflows/{{workflowId}}/start` with valid token and valid body.  
2. Capture HTTP status and body.  
3. Repeat with: no token, empty header, malformed header, invalid token, expired token.  
4. For each negative case, capture status and body.  
5. Verify success only occurs for valid token; all other variants are rejected.

**Expected HTTP Status**  
- Positive: 200 or 201.  
- Negative: 401 or 403.

**Expected Response Behaviour**  
- Positive: Returns an execution object identifier and minimal non-sensitive metadata.  
- Negative: Returns an error without any sensitive internal details; no execution is created.

**Expected Security Behaviour**  
- Only authenticated callers with valid tokens can start workflows.  
- No anonymous or invalid-token caller can start execution.

**Expected State / Side Effect**  
- Positive: One new execution record created with owner = Standard User A / Tenant A.  
- Negative: No new execution records created.

**Validation Criteria**  
- For positive case: execution starts; token subject matches owner.  
- For negative cases: status is 401/403; no execution ID is returned; audit logs (if available) show rejected authentication.

**Failure Criteria**  
- Any negative case returns 200/201 and an execution ID.  
- Or negative case returns 500 with stack trace.  
- Or anonymous caller can start workflows.

**Potential Vulnerability if Failed**  
Broken Authentication for critical workflow start (OWASP API2).

**Context Required**  
YES — Authentication scheme, token format, and expected authz rules.

**Automation Feasibility**  
Fully Automatable in Postman.

**Postman Folder**  
01_Authentication

**Postman Request Name**  
SEC_API_AUTH_001 - Workflow Start Authentication

**Required Variables**  
- `baseUrl`  
- `workflowId`  
- `validUserAToken`  
- `invalidToken`  
- `expiredToken`

**Setup Dependency**  
- API call or fixture to obtain `validUserAToken` and create `workflowId` if not static.

**Cleanup Dependency**  
- Optional deletion of created execution to avoid test data build-up.

## SEC_API_BOLA_001 — Cross-Tenant Execution Access

**Test Case ID**  
SEC_API_BOLA_001

**Test Case Name**  
Verify Tenant A Cannot Retrieve Tenant B Execution

**API Name**  
OpenAPI definition

**Endpoint**  
/api/v1/executions/{executionId}

**HTTP Method**  
GET

**Operation ID**  
getExecution

**Security Category**  
Broken Object Level Authorization (BOLA) / Tenant Isolation

**OWASP Mapping**  
API1:2023, API3:2023, API8:2023, API10:2023

**CWE Mapping**  
CWE-284 (Improper Access Control)

**Security Objective**  
Ensure an authenticated user from Tenant A cannot access execution details of Tenant B by manipulating `executionId`.

**Risk**  
Critical

**Priority**  
P1

**Preconditions**  
- Execution E1 exists for Tenant A.  
- Execution E2 exists for Tenant B.  
- Tenant A user has token `tenantAUserToken`.  
- Tenant B user has token `tenantBUserToken`.

**Authentication Context**  
- Tenant A Standard User token.  
- Tenant B Standard User token.

**Required User / Role**  
- Tenant A User A.  
- Tenant B User B.

**Required Tenant Context**  
- Tenant A for Execution E1.  
- Tenant B for Execution E2.

**Required Test Data**  
- `executionIdA` (Tenant A).  
- `executionIdB` (Tenant B).

**Request Headers**  
- `Authorization: Bearer {{tenantAUserToken}}`.

**Path Parameters**  
- `executionId = {{executionIdB}}` (target tenant B execution).

**Query Parameters**  
- None.

**Request Body**  
- None.

**Security Manipulation**  
- Substitute `executionIdA` with `executionIdB` while keeping Tenant A token.

**Execution Steps**  
1. Call GET `/api/v1/executions/{{executionIdA}}` with Tenant A token; verify success as baseline.  
2. Call GET `/api/v1/executions/{{executionIdB}}` with Tenant A token.  
3. Capture status and response body.  
4. Optionally call GET `/api/v1/executions/{{executionIdB}}` with Tenant B token to confirm valid access for owner.

**Expected HTTP Status**  
- Baseline (own): 200.  
- Cross-tenant: 403 or 404.

**Expected Response Behaviour**  
- Cross-tenant request does not return execution details for Tenant B.  
- Error message is generic, no tenant info leaked.

**Expected Security Behaviour**  
- Object-level and tenant-level authorization prevents cross-tenant read access.

**Expected State / Side Effect**  
- No change to any execution state for cross-tenant request.

**Validation Criteria**  
- For cross-tenant request: response body must not contain Tenant B identifiers (tenantId, workflowDefinitionId, details, errorMessage).  
- Audit logs (if available) show denied access.

**Failure Criteria**  
- Cross-tenant request returns 200 and includes Tenant B data.  
- Or returns verbose error revealing tenant or internal details.

**Potential Vulnerability if Failed**  
BOLA and tenant isolation failure exposing cross-tenant execution details.

**Context Required**  
YES — Tenant model, error-handling policy.

**Automation Feasibility**  
Fully Automatable in Postman.

**Postman Folder**  
02_Authorization_BOLA

**Postman Request Name**  
SEC_API_BOLA_001 - Cross-Tenant Execution Access

**Required Variables**

- `tenantAUserToken`  
- `tenantBUserToken`  
- `executionIdA`  
- `executionIdB`

**Setup Dependency**  
- Pre-create executions E1 and E2 via workflow start or fixtures.

**Cleanup Dependency**  
- Optional termination/deletion of executions.

High

- Unauthorized or cross-tenant attempt: 403 or 404.

**Expected Response Behaviour**  
- Unauthorized change is rejected; assignee remains original.  
- Response does not expose internal authorization rules.

**Expected Security Behaviour**  
- API enforces ownership/role checks before allowing assignee change.  
- Ignores or rejects server-controlled fields like `tenantId` if present.

**Expected State / Side Effect**  
- For rejected cases: no change to task assignee or tenantId.  
- For allowed case: assignee updated only when policy permits.

**Validation Criteria**  
- Verify via follow-up GET that assignee did not change in unauthorized scenarios.  
- Ensure tenantId and other server-managed fields remain unchanged.

**Failure Criteria**  
- Unauthorized user can change assignee.  
- Cross-tenant assignment succeeds.  
- Submitted tenantId or other privileged fields are persisted.

**Potential Vulnerability if Failed**  
Mass assignment leading to privilege escalation or cross-tenant task control.

**Context Required**  
YES — Business rules for who may reassign tasks.

**Risk**  
Critical

**Priority**  
P1

**Authentication Context**

**Required Tenant Context**  
Tenant A.

**Required Test Data**  
- `executionIdA` for E1.

**Request Headers**  
- `Authorization: Bearer {{privilegedToken}}` or `{{lowPrivilegeToken}}`.

**Path Parameters**  
- `executionId = {{executionIdA}}`.

**Query Parameters**  
- None.

**Request Body**  
```json
{
  "reason": "Test termination"
}
```

**Security Manipulation**

**Execution Steps**
