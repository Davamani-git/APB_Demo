# Orchestration Service API Security Analysis

## SECTION 1 — SECURITY ANALYSIS SUMMARY

- **API Name:** OpenAPI definition (Orchestration/Workflow & Configuration Service)
- **API Version:** v0
- **OpenAPI Version:** 3.1.0
- **Defined Servers:**
  - https://dev2.aava.ai/orch-service
- **Base URL:** https://dev2.aava.ai/orch-service
- **Base Path (effective from server + paths):**
  - `/api/v1/...` (workflow/execution/task APIs)
  - `/orch-service/config/...` (configuration/cache APIs)
  - `/` and `/test` root endpoints
- **Total Paths:** 27
- **Total API Operations (method+path):** 27
  - PUT: 1
  - POST: 13
  - GET: 11
  - DELETE: 2

### Authentication Mechanisms (from spec)

- **Defined security schemes:** None in `components.securitySchemes`.
- **Global security:** None (`security` missing at root level).
- **Operation-level security:** None (`security` missing in operations).

Therefore, from Swagger alone, **no explicit authentication mechanism** is documented.
Runtime implementation may enforce auth (e.g., via gateway), but that is **not visible in this spec**.

### Specification Validity

- Parsed as valid OpenAPI 3.1.0 JSON.
- Core sections present: `openapi`, `info`, `servers`, `paths`, `components.schemas`.
- **Missing / malformed sections:**
  - `components.securitySchemes` (missing)
  - `security` (global) (missing)
  - No `responses` content schemas for many `200` responses (e.g., task decision/terminate endpoints just say `"description":"OK"`).
  - No explicit error response codes (e.g., 400/401/403/404/429/500) documented.

Classification: **Valid but Security-Incomplete**.

### High-level Functional Areas

- **Workflow Management:**
  - Upload workflows
  - Start workflow executions
  - Terminate executions
  - User task lifecycle (approve/reject/skip/return, runtime-input, assignee update)
  - Read executions, tasks, events, Temporal executions
- **Configuration Management:**
  - Read configuration values, maps, keys, health, categories
  - Cache info and contents (raw and all cached configs)
  - Refresh and sync configurations (category/environment/beans/all)
  - Cache eviction (single key, bulk, clear-all)
- **Root/Test Endpoints:** `/` and `/test` returning simple maps.

### Surface Area Metrics

- **Potential BOLA (Broken Object Level Authorization) Surfaces:** 12
  - Most execution & task endpoints with identifiers: `taskId`, `executionId`, `workflowId/runId`, config keys/categories.
- **Potential BOPLA / Mass Assignment Surfaces:** 6
  - Workflow upload and various request bodies allowing arbitrary maps/strings, control properties (status/decisionType/tenantId etc.).
- **Potential BFLA (Broken Function Level Authorization) Surfaces:** 9
  - Approve/reject/skip/return tasks; terminate execution; config refresh/sync; cache clear/evict bulk.
- **Potential Injection Surfaces:** 7
  - `UploadWorkflow` body (text/plain & generic object); `userInputs` maps; `payload` in events; generic config maps.
- **Potential SSRF Surfaces:** 0
  - No obvious URL/host fields exposed by this spec.
- **Sensitive Data Endpoints:** 8
  - Execution, node execution, user task, runtime event responses; configuration maps; workflow upload.
- **Tenant-Aware APIs:** 7
  - Headers: `X-Tenant-Id`, fields: `tenantId` in multiple response DTOs.
- **File APIs:** None (no `multipart/form-data` or binary file schemas).
- **Business Critical APIs:**
  - Workflow control: `/api/v1/workflows`, `/api/v1/workflows/{id}/start`, `/api/v1/executions/{executionId}/terminate`.
  - User task decisions: approve/reject/skip/return/runtime-input.
  - Config and cache bulk operations: refresh/sync/all/clear/evict bulk.

## SECTION 3 — AUTHENTICATION ANALYSIS

### Authentication Scheme & Security Definitions

- **Authentication Scheme:** Not documented in OpenAPI.
- **Security Scheme Name:** N/A
- **Authentication Location:** N/A (no `securitySchemes`, no `security` on operations).
- **Global vs Endpoint Level:** No `security` at root, no `security` per operation.
- **OAuth Scopes:** None documented.

### Public APIs (per Swagger)

Because no authentication requirements are declared, **all endpoints appear as publicly callable from the contract perspective**.
This does **not** mean they are truly public at runtime.

We mark all endpoints that perform sensitive actions or expose tenant/execution/task data as:

- **Potential Public Exposure — Runtime Validation Required**

- `/api/v1/workflows/{id}/start`
- `/api/v1/executions/{executionId}` and related task/event endpoints
- `/api/v1/tasks/{taskId}/approve|reject|skip|return|runtime-input|assignee`
- `/orch-service/config/refresh/*`, `/orch-service/config/sync`, `/orch-service/config/cache/*`

- **SEC-CONF-001:** No `securitySchemes` defined — authentication mechanism is undocumented.
- **SEC-CONF-002:** No global or operation-level `security` — impossible to distinguish public vs protected endpoints.
- **SEC-CONF-003:** Tenant header (`X-Tenant-Id`) is optional and not bound to any documented auth context.

Classification: **Security Misconfiguration Suspected / Additional Context Required**.

## SECTION 13 — BUSINESS LOGIC SECURITY

Format: `API / Workflow | Potential Flow | Potential Abuse | Context Required | Risk`

1. **Workflow Execution Lifecycle**
   - Flow (Inferred Business Workflow): `uploadWorkflow` → `startExecution` → task operations (`approve/reject/skip/return/runtime-input`) → `terminateExecution`.
   - Potential Abuse: Start or manipulate executions for workflows the caller should not control; skip approval steps; repeatedly terminate/retry to affect downstream processes.
   - Context Required: Role matrix for workflow designers, approvers, and users; ownership rules for executions/tasks.
   - Risk: Critical.

2. **User Task Decision Flow**
   - Flow: `getExecutionTasks` → `[approve | reject | skip | return | runtime-input]` on `/api/v1/tasks/{taskId}`.
   - Potential Abuse: Unauthorized users performing decisions; decisionType/targetNodeId enabling jumps in the workflow; comments/inputs injecting malicious content.
   - Context Required: Mapping of task statuses, allowed transitions per role.
   - Risk: High.

3. **Configuration & Cache Maintenance Flow**
   - Flow: `getConfigurations`/`getConfigurationValue` → `refresh*` → `cache/evict` & `cache/clear` → `cache/all/raw/info`.
   - Potential Abuse: Unauthorized refreshes affecting system behavior; clearing cache to disrupt service; reading raw configs leaking secrets; selective eviction to bypass feature flags/security.
   - Context Required: Which categories contain secrets/security-critical values; which roles operate config endpoints.
   - Risk: Critical for cache/raw/all; High for refresh/sync/clear.

4. **Temporal Execution Flow**
   - Flow: `startExecution` (assumed) → `getExecutionInTemporal` (`executionId/temporal`).
   - Potential Abuse: Extracting internal Temporal workflow IDs; using them to query other systems; possible cross-system leakage.
   - Context Required: Temporal integration and its auth model.
   - Risk: Medium–High.

All marked as **Business Context Required** for final evaluation, with strong recommendation for business-logic tests (workflow skipping, out-of-order execution, unauthorized approval/cancellation, replay).
