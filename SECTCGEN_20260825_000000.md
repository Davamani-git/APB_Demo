### 4.1 `/api/v1/workflows/{id}/start` — POST (startExecution)

#### SEC_API_AUTH_001

- **Test Case ID:** SEC_API_AUTH_001
- **Test Case Name:** Verify `/startExecution` requires valid authentication
- **API Name:** OpenAPI definition (orch-service workflow and configuration APIs)
- **Endpoint:** /api/v1/workflows/{id}/start
- **HTTP Method:** POST
- **Operation ID:** startExecution
- **Security Category:** Authentication
- **OWASP Mapping:** API2:2023 (Broken Authentication), API8:2023 (Security Misconfiguration)
- **CWE Mapping:** CWE-306 (Missing Authentication for Critical Function)
- **Security Objective:** Ensure the startExecution operation cannot be invoked without valid authentication and that undocumented auth is enforced server-side.
- **Risk:** Critical
- **Priority:** P1
- **Preconditions:**
  - Workflow with ID `{workflowId}` exists and is startable.
  - Application is deployed at `https://dev2.aava.ai/orch-service`.
- **Authentication Context:**
  - Valid authenticated user token (actual mechanism unknown).
  - Context Required = YES (auth scheme, header name, token format).
- **Required User / Role:**
  - "Privileged User" allowed to start executions.
  - Role Context Required = YES.
- **Required Tenant Context:**
  - Tenant A with a valid `X-Tenant-Id` value.
- **Required Test Data:**
  - `workflowId` belonging to Tenant A.
  - Example `StartExecutionRequest` body with reasonable `user`, `realmId`, `hierarchyLevel`, `hierarchyEntityId`, `userInputs`.
- **Request Headers:**
  - Positive case: `Authorization: Bearer {{validToken}}` (or applicable scheme — Context Required).
  - `X-Tenant-Id: {{tenantAId}}` (optional per spec but used in tests).
  - `Content-Type: application/json`.
- **Path Parameters:**
  - `id = {{workflowId}}`.
- **Query Parameters:**
  - None.
- **Request Body:**
  ```json
  {
    "user": {{userId}},
    "realmId": {{realmId}},
    "hierarchyLevel": "LEVEL_1",
    "hierarchyEntityId": {{hierarchyEntityId}},
    "userInputs": {
      "field1": "value1"
    },
    "inputMode": "DEFAULT"
  }
  ```
- **Security Manipulation:**
  - Scenario A: No authentication header.
  - Scenario B: Empty Authorization header (`"Authorization": ""`).
  - Scenario C: Malformed Authorization header (e.g., `"Authorization": "Bearer"`).
  - Scenario D: Invalid token (`"Authorization": "Bearer invalid-token"`).
  - Scenario E: Expired token (if available).
- **Execution Steps:**
  1. Configure Postman environment with `baseUrl`, `workflowId`, `tenantAId` and token variables.
  2. For Scenario A, send POST `{{baseUrl}}/api/v1/workflows/{{workflowId}}/start` without `Authorization` header, with valid body and optional `X-Tenant-Id`.
  3. Capture HTTP status and response body.
  4. Repeat for Scenario B–E using respective Authorization header manipulations.
  5. As a control, send the same request with a valid token and correct headers.
- **Expected HTTP Status:**
  - Negative scenarios: 401 Unauthorized or 403 Forbidden.
  - Positive control: 200 OK.
- **Expected Response Behaviour:**
  - Negative: Error response of type `AAVAResponse*` (or equivalent) with no execution started, no `executionId` returned.
  - Positive: `StartExecutionResponse` with valid `executionId` and `correlationId`.
- **Expected Security Behaviour:**
  - Unauthenticated or invalidly authenticated requests must not start executions.
  - Security control should validate presence and correctness of auth tokens.
- **Expected State / Side Effect:**
  - Negative: No new execution is created in the system.
  - Positive: Exactly one new execution is created.
- **Validation Criteria:**
  - Negative: Status is 401/403; response body does not contain `executionId` or indicates error; backend logs (if available) show rejected auth.
  - Positive: Status 200; response includes numeric `executionId`; execution visible via `/api/v1/executions/{executionId}`.
- **Failure Criteria:**
  - Status 200 with valid `executionId` for any unauthenticated/invalid token scenario.
  - Or any indication that execution started without proper authentication.
- **Potential Vulnerability if Failed:**
  - Broken Authentication for startExecution (unauthorized workflow execution start).
- **Context Required:** YES (auth scheme, roles).
- **Automation Feasibility:** Fully Automatable in Postman (assuming tokens are provided).
- **Postman Folder:** 01_Authentication
- **Postman Request Name:** SEC_API_AUTH_001 - StartExecution Requires Auth
- **Required Variables:**
  - `baseUrl`, `workflowId`, `tenantAId`, `validToken`, `expiredToken`, `invalidToken`.
- **Setup Dependency:**
  - Workflow upload and retrieval to get `workflowId` (e.g., via `/api/v1/workflows`).
- **Cleanup Dependency:**
  - Optional: Terminate created execution via `/api/v1/executions/{executionId}/terminate`.

#### SEC_API_BOPLA_001

- **Test Case ID:** SEC_API_BOPLA_001
- **Test Case Name:** Prevent client-controlled `user`/`realmId` overriding server context on startExecution
- **API Name:** OpenAPI definition
- **Endpoint:** /api/v1/workflows/{id}/start
- **HTTP Method:** POST
- **Operation ID:** startExecution
- **Security Category:** BOPLA / Mass Assignment
- **OWASP Mapping:** API3:2023 (Broken Object Property Level Authorization), API6:2023 (Sensitive Business Flows)
- **CWE Mapping:** CWE-915 (Improperly Controlled Modification of Dynamically-Determined Object Attributes)
- **Security Objective:** Ensure server does not trust client-supplied `user`, `realmId`, `hierarchyEntityId` for authorization or tenancy decisions.
- **Risk:** High
- **Priority:** P1
- **Preconditions:**
  - Tenant A and Tenant B exist.
  - Workflow `workflowIdA` belongs to Tenant A.
- **Authentication Context:**
  - Valid token for Standard User A (Tenant A).
- **Required User / Role:**
  - Standard User A is allowed to start executions only for themselves and their realm.
- **Required Tenant Context:**
  - Tenant A ID (`tenantAId`).
- **Required Test Data:**
  - `userIdA`, `userIdB`.
  - `realmIdA`, `realmIdB`.
- **Request Headers:**
  - `Authorization: Bearer {{userAToken}}`.
  - `X-Tenant-Id: {{tenantAId}}`.
- **Path Parameters:**
  - `id = {{workflowIdA}}`.
- **Request Body (attack variant):**
  ```json
  {
    "user": {{userIdB}},
    "realmId": {{realmIdB}},
    "hierarchyLevel": "LEVEL_1",
    "hierarchyEntityId": {{hierarchyEntityId}},
    "userInputs": {
      "amount": "1000"
    },
    "inputMode": "DEFAULT"
  }
  ```
- **Security Manipulation:**
  - Change `user` and `realmId` to represent another user/realm (B) while authenticated as User A.
- **Execution Steps:**
  1. Authenticate as User A, obtain `userAToken`.
  2. Confirm a baseline execution with `user` = `userIdA`, `realmId` = `realmIdA` works.
  3. Send POST startExecution with body where `user` and `realmId` are set to User B / Realm B.
  4. Capture status and response body.
  5. If execution is created, retrieve details via `/api/v1/executions/{executionId}`.
- **Expected HTTP Status:**
  - 400/403/422 (depending on validation) for manipulated properties.
- **Expected Response Behaviour:**
  - Error indicating invalid request or unauthorized context; no execution started for B under A’s token.
- **Expected Security Behaviour:**
  - Server must ignore or reject attempts to set another user/realm via request body; the execution must be tied to authenticated user/tenant, not request payload.
- **Expected State / Side Effect:**
  - No execution created with `tenantId` or user context of B.
- **Validation Criteria:**
  - Execution, if created, must show `tenantId`/user equal to A, not B.
  - Preferably, execution is not created at all for such manipulated payload.
- **Failure Criteria:**
  - Execution created where `tenantId` or user/realm reflect values from client payload conflicting with authenticated context.
- **Potential Vulnerability if Failed:**
  - Broken property-level authorization leading to cross-tenant or impersonation issues when starting executions.
- **Context Required:** YES (precise mapping of body fields to authorization logic).
- **Automation Feasibility:** Fully Automatable in Postman.
- **Postman Folder:** 03_Authorization_BOPLA
- **Postman Request Name:** SEC_API_BOPLA_001 - StartExecution Property Override
- **Required Variables:**
  - `baseUrl`, `userAToken`, `workflowIdA`, `userIdA`, `userIdB`, `realmIdA`, `realmIdB`, `tenantAId`.
- **Setup Dependency:**
  - User and tenant test data creation out-of-band.
- **Cleanup Dependency:**
  - Terminate any created execution used for validation.

- **Risk:** High
- **Priority:** P1
- **Preconditions:**

  - Workflow `workflowIdB` belongs to Tenant B.
- **Authentication Context:**
  - Valid token for Tenant A user.
- **Required User / Role:**
  - Standard Tenant A user.
- **Required Tenant Context:**
  - `tenantAId`, `tenantBId`.
- **Required Test Data:**
  - `workflowIdB` (Tenant B’s workflow).
- **Request Headers:**
  - `Authorization: Bearer {{tenantAUserToken}}`.
  - `X-Tenant-Id: {{tenantBId}}` (malicious attempt).
- **Path Parameters:**
  - `id = {{workflowIdB}}`.
- **Request Body:**
  - Valid `StartExecutionRequest` with typical values.
- **Security Manipulation:**
  - Combine Tenant A token with Tenant B path ID and header `X-Tenant-Id`.
- **Execution Steps:**
  1. Authenticate as Tenant A user.
  2. Send POST startExecution for `workflowIdB` with `X-Tenant-Id` = `tenantBId`.

- **Validation Criteria:**
  - Absence of `executionId` in response OR execution with `tenantId` corresponding to Tenant A’s legitimate scope only.
- **Failure Criteria:**
  - Execution created with `tenantId` = Tenant B or workflow running under Tenant B context.
- **Potential Vulnerability if Failed:**
  - Cross-tenant execution start; Broken Tenant Isolation.
- **Context Required:** YES (exact tenant mapping between token and headers).
- **Automation Feasibility:** Fully Automatable in Postman (with tenant test data).
- **Postman Folder:** 04_Tenant_Isolation
