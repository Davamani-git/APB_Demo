### Architecture and Design Decisions

As the Senior UI Engineer for this project, I made specific architectural and design choices to ensure the application is modular, maintainable, secure, and provides a high-quality user experience, aligning with standards expected in financial institutions.

**1. Technology Stack Selection:**
-   **AngularJS 1.8.x:** Chosen as per the explicit requirement. This version is the final Long-Term Support (LTS) release, ensuring maximum stability for a legacy framework. My implementation uses the 'controller as' syntax (`DashboardController as vm`) and avoids direct `$scope` manipulation where possible, which is a step towards modern component-based architecture and makes the code cleaner and more testable.
-   **Bootstrap 5:** Selected for its robust, mobile-first responsive grid system and pre-styled components. This accelerates UI development and guarantees a consistent look and feel across all devices. Bootstrap's CSS custom properties (`--bs-primary`, etc.) are overridden at the `:root` level to apply the bank's brand palette globally, so buttons, badges, progress bars, and pills all pick up the theme without touching individual component markup.
-   **Chart.js 2.9.4 & angular-chart.js 1.1.1:** This combination was specified and is a reliable choice for data visualization within an AngularJS context. It provides a declarative way to create charts (`<canvas chart-doughnut>`), separating chart logic from the controller.
-   **Google Fonts (Work Sans):** Loaded to match the bold, clean sans-serif typography used across modern retail-banking digital properties, replacing the default Bootstrap system font stack.

**2. Application Architecture (MVVM-inspired MVC):**
-   **Model-View-Controller (MVC):** The application strictly follows the separation of concerns principle inherent in AngularJS's MVC pattern.
    -   **Model:** Represented by the data structures within `dataService.js`. This service acts as the single source of truth for all application data — both **Cards** (credit card products, transactions) and **Accounts** (current/savings accounts, account transactions). In a real-world scenario, this service would be the sole point of interaction with a backend/core-banking API, encapsulating all HTTP logic.
    -   **View:** The `index.html` file serves as the declarative template. It contains no business logic and is responsible only for presenting the data provided by the controller.
    -   **Controller (`dashboardController.js`):** This acts as the orchestrator or ViewModel (in MVVM terms). It fetches data from the `dataService`, processes it into a format suitable for the view, and exposes data and functions to the view via the `vm` (ViewModel) object. It handles user interactions (clicks, filters, sorting, navigation) and updates the view accordingly.

-   **Banking Menu / Section Switching:** The app exposes a top-level navigation (`vm.activeSection`) with two entries — **Accounts** and **Cards** — mirroring how a real retail-banking app segments products. Both sections share the same controller and data service instance; switching sections toggles visibility (`ng-show`) rather than triggering a route change, keeping the single-page, buildless nature of the demo intact while still reading like two distinct product areas.

-   **Service-Oriented Design:**
    -   The `dataService.js` is a critical design choice. All business logic (filtering, sorting, aggregation, calculations for metrics, charts, and account cash-flow summaries) is encapsulated within this service. This makes the controller lean and focused on view-related logic. It also promotes reusability and simplifies unit testing, as the data logic can be tested in isolation. Cards and Accounts follow an identical internal pattern (mock dataset → generator function → filter/summary functions), so adding a further banking capability (e.g. loans, budgets) means extending the same service rather than introducing a new architectural pattern.

**3. PCI-DSS / Data Protection Compliance Mindset:**
-   **Data Masking:** As per PCI DSS Requirement 3.3, credit card numbers in the mock data are masked (`XXXX-XXXX-XXXX-4567`). Account identifiers follow the equivalent convention for deposit accounts: the IBAN is displayed with only the last segment visible (`ES91 XXXX XXXX XXXX 4521`), consistent with how the account number itself is masked. This is a fundamental practice to prevent accidental exposure of sensitive account and Primary Account Numbers (PAN) on screen.
-   **No Client-Side Storage of Sensitive Data:** The application does not use `localStorage` or `sessionStorage` to persist sensitive information. While a dark mode preference could be stored, no transactional, balance, or account data would ever be placed there.
-   **Secure API Communication (Simulated):** Comments within `dataService.js` explicitly state that in a production environment, all communication with a backend must occur over HTTPS to protect data in transit (PCI DSS Req 4.1).
-   **Separation of Concerns:** The architecture itself is a security feature. By isolating data access to a service, we create a clear boundary that can be secured and audited. The view never directly accesses or manipulates raw data.

**4. Brand & Localization:**
-   **Santander-inspired visual system:** The UI was re-themed to reflect Banco Santander's public brand language — signature red (`#EC0000`), bold sans-serif headings, white/light section backgrounds, and pill-shaped navigation/buttons — implemented purely through color tokens, typography, and layout, referencing the publicly viewable `santanderdigitalservices.com` site for calibration. The application does **not** embed Santander's actual logo mark or any other copyrighted/trademarked asset; the header uses a generic landmark icon plus a text wordmark, the same treatment the original demo used for its placeholder "Europe Bank" brand. This keeps the demo clearly a UI reference build rather than a reproduction of a protected brand asset.
-   **Currency localization:** All monetary values are formatted as Euros via a dedicated `EUR` Angular filter (`Intl.NumberFormat('es-ES', { style: 'currency', currency: 'EUR' })`), replacing the original INR/`en-IN` formatting. Mock data magnitudes (credit limits, balances, per-transaction amounts) were rescaled to realistic Euro figures rather than simply relabeling the original Rupee-scale numbers.
-   **Market-appropriate mock data:** Merchant names, payment references, and branch locations were localized to pan-European/Spanish equivalents (e.g. Carrefour, Deliveroo, Repsol, Iberdrola, Madrid/Barcelona/Valencia branches, and a "Bizum Payment" transaction category reflecting Spain's popular P2P payment rail) so the demo data reads as coherent with the currency and brand, not just relabeled.

**5. User Experience (UX) and Feature Implementation:**
-   **Loading State:** An initial loading spinner prevents the user from seeing a jarring flash of un-styled or incomplete content. This improves perceived performance and provides feedback that the application is working.
-   **Responsiveness:** A mobile-first approach using Bootstrap ensures the dashboard is fully functional and readable on devices ranging from small phones to large desktops.
-   **Interactivity:** Features like real-time filtering, column sorting, and modal popups create a dynamic and engaging experience, allowing users to explore their data intuitively — implemented consistently for both the Cards transaction table and the Accounts transaction table.
-   **Advanced Features:**
    -   **Dark Mode:** Implemented by toggling a class on the `<body>` tag. This is a modern accessibility and user-preference feature that demonstrates attention to detail, and remains fully themed under the Santander color system.
    -   **CSV Export:** A practical utility for users who need to perform offline analysis, available independently for card transactions and account transactions. The logic is handled entirely on the client side for this demonstration.
    -   **Forecasting & Analysis:** The inclusion of a spend forecast, top categories, top merchants, and (on the Accounts side) a monthly credits/debits/net-flow summary elevates the application from a simple data display to a true analytical tool, providing actionable insights to the user.
